SKYBREAK · campaign architecture · October 24, 2026

27 worlds.
One campaign.

Yes, we can build 27+ unique missions in one Roblox experience—and we can initially run them in one place. The scalable approach is to load one mission world per server at a time, rather than keep 27 detailed worlds alive together.

This is a proposed production plan, not a claim that these levels or performance results already exist. The current game has one island mission, four save slots, authoritative combat, and a working React interface.

My recommendation

Start with a modular, single-place campaign. Prove three very different maps on real phones. Keep the mission format portable so large chapters can move to separate places later.

Creative direction

27 individually designed combat arenas, grouped into three story acts. Reuse an art kit, but change geography, landmarks, routes, lighting, and objectives—not just the sky color.

What “one game” means

A Roblox experience can contain multiple places. Each place is its own environment and code deployment. Players can still see one game listing and one campaign even when chapters use different places. Roblox place structure ↗

Choose the loading architecture

Crucial distinction: ServerStorage avoids sending unused models to clients, but it still stores those models on the server. Streaming reduces client-loaded Workspace content; it does not make 27 running worlds, their AI, or stored map templates free. ServerStorage ↗ · Streaming scope ↗

How a single-place campaign would work

  1. Choose and validate. The server checks the selected slot and unlocked mission. A catalog resolves stable mission IDs to world, objective, environment, and enemy definitions.
  2. Prepare a transition. Fade to a loading view; suspend flight and combat. Save the previous result using the existing serialized persistence queue. A failed save stays pending and clearly marked.
  3. Dispose of the old world. End AI loops, disconnect events, remove missiles and effects, clear mission-owned terrain, and release caches and references. Track everything under one mission lifecycle.
  4. Load only the selected map. Build from compact definitions or instantiate a tested asset package. Keep large future maps out of ReplicatedStorage. Preload only critical current-mission assets, with a timeout and retry path.
  5. Set the environment and check readiness. Apply the sky, atmosphere, time, music, and weather. Wait for the aircraft, spawn area, and essential content before handing back control.
  6. Run and complete. Server-authoritative objective logic decides the result. Record the mission-specific outcome and unlocks; offer retry, next mission, or return to campaign.

Destroying instances does not guarantee all asset caches disappear immediately. Repeated mission transitions need a memory soak test. Loading the next map before removing the previous one can temporarily double active map costs; budget that peak or use a loading screen between teardown and creation.

Multiplayer changes the answer

For the first expansion, assume solo campaign or one cooperating party sharing one mission per server. The current per-player combat sessions are not yet a full multiplayer mission-world manager. A global map swap would interrupt everyone else in that server.

If players must choose different missions concurrently, route each party to a separate reserved mission server. A single mission-runner place can host many server instances, each loading a different mission. Later, chapter places can also separate heavy content. Avoid making 27 overlapping private worlds in a single shared Workspace.

Cross-server travel needs server-initiated teleports, failed-transfer recovery, destination authorization, and a loading screen. Teleport payloads are not authoritative progress. Roblox teleports must be tested in a published Roblox client, not Studio. Our current unpublished project therefore cannot validate that path yet. Teleport guide ↗

A unique sky for every mission?

Yes. A Sky object in Lighting uses six images for a custom skybox. Author and upload coherent cube faces, then associate their asset IDs with an environment preset. Test seams and sun alignment, and preload only the next required environment. Custom skyboxes ↗

Environment preset

Skybox, sun and moon settings, clock time, exposure, atmosphere, color grading, clouds, fog, ambient audio, and modest weather effects. One coordinated palette gives each location an identity.

Presentation boundaries

One shared mission can use one server-wide Lighting setup. Different players can have local presentation presets, but that does not isolate world geometry, terrain, server weather, or gameplay. Separate mission servers are simpler for unrelated worlds.

The sky is a distant backdrop, not explorable terrain. Build flyable mountain silhouettes, cloud corridors, bridges, and landmarks as actual world content where players need depth and interaction. Keep haze artistic without hiding enemies or missile warnings.

Performance: what actually scales

“27 levels” is not a frame-rate budget. Visible geometry, texture variety, transparency, active enemies, physics, network updates, and retained content matter. The following are proposed acceptance goals, not measured results or Roblox limits.

Flight needs special streaming care

Our current jet travels at roughly 165–320 studs per second, and locks can reach 2,450 studs. A streaming radius comfortable for walking can leave a pilot approaching unloaded scenery or targeting an aircraft model absent on the client.

Keep replication focused on the plane—the game already does this—and test forward motion, rapid turns, respawns, and distant targets. Make target indicators tolerate missing models by using validated target IDs and position telemetry. Load collision and essential objectives before starting flight. Do not mark whole maps persistent just to hide streaming bugs. Streaming settings belong in place configuration; they are not a per-mission runtime toggle. Engine streaming behavior ↗

27 mission concepts to make the system concrete

These are design proposals. Every entry gets a distinct arena and landmark; shared modular assets keep production manageable. New objective types require new gameplay systems—this is more than copying the current three-plane encounter.

What changes in this repository

Mission data and world ownership

Replace the single WorldBuilder entrypoint with a MissionCatalog plus MissionLoader. Each mission specifies world ID, environment ID, spawn, bounds, objective graph, enemy waves, and next unlocks. Return a disposable mission session that owns geometry, terrain regions, timers, sounds, and effects.

CombatService should accept mission rules rather than fixed three-kill victory. Separate objective evaluation from flight simulation so escort, interception, ground strikes, and boss phases reuse the same reliable controls.

Four save slots, now with real campaign progression

Keep four slots, but evolve each to store schema version, current mission ID, unlocked IDs, and per-mission completion/best time/rank. Migrate a completed v1 save to mission 01 completed and mission 02 unlocked—not all 27 completed. Preserve the existing queue and retry behavior; use idempotent completion records.

Data stores are shared across places in the same experience. If we split servers, add explicit session ownership/handoff so an old server cannot overwrite newer progress. Validate mission eligibility at the destination and do not rely on client-supplied progress. Data stores ↗

Art and source-control policy

Keep canonical, reproducible inputs in Git: code, mission definitions, manifests, and essential authored geometry data. Keep generated exports, builds, caches, and previews ignored. Our current Blender generators are the aircraft authoring source; their mesh JSON remains a tracked build input so ordinary builds do not require Blender.

For future hand-edited Blender scenes, the .blend may become irreplaceable source and should be backed up/versioned, potentially with Git LFS or external asset storage. Do not apply today’s generated-file cleanup rule blindly to future artwork. Upload runtime assets to Roblox and retain an asset-ID/version manifest; never make an unbacked-up local folder the only copy.

A sensible rollout

  1. Build the campaign foundation. Catalog, loader/unloader, save migration, environment presets, next/retry flow, and objective abstraction. Keep mission 01 working throughout.
  2. Make three vertical slices. Island dogfight, dense canyon interception, and night city escort. These expose different visibility, streaming, memory, and objective problems.
  3. Measure and choose the deployment shape. If one-place storage, joins, or transitions exceed our measured budgets, split chapters. Otherwise retain the simpler one-place flow. Publish a staging experience to test real devices, persistence, and any teleports.
  4. Produce act I, then expand. Build reusable terrain/building kits and a mission validator. Test nine missions before committing to the remaining eighteen. Make 27+ a data/content expansion, not 27 forks of game code.
  5. Release gates. Check every level on phone/PC/controller; save/rejoin/retry; repeated transitions; lost connections; missing assets; slow devices; and multiplayer isolation where supported.

My architectural preference: one coherent campaign, one loaded mission per server, and a place-independent mission format. That gives us the simplest next step without locking us into a giant all-in-one map later.

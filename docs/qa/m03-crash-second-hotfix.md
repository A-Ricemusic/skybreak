## Findings and ranked hypotheses

1. **Client terrain memory/render pressure (medium confidence, leading hypothesis after mobile app-exit clarification).** M03 still emits a continuous 30,976 × 30,976 × 4 bottom floor in addition to its shell. Standalone Luau counts: 29,567 ops, 30,590 jobs, 206,784,672 voxel writes; floor alone is 59,969,536 writes (29%). TerrainState records prior observed M03 native clears of 17.6 s and 9–23 s even after Air-filling. D-120 records M04/M05 floor removal reducing terrain work/chunk allocation; those worlds already omit it. Writes are not resident-memory measurements. This PR removes only M03's inaccessible floor, leaving 146,815,136 writes; all caps, LOD walls, perimeter curtains, foundations and target poses stay unchanged. Existing exhaustive cap/curtain coverage tests remain.
2. **Military mesh/PBR memory or preload spike (low-to-medium confidence).** Before this PR M03 places 9 Radar + 4 AA decorations (13 Models, 13 MeshParts, 13 SurfaceAppearances for the current export); M02 places 4 AA, M01 zero military assets. M03 uses TWO unique kit assets, not ten. The server Preload requested ten but cached templates are unparented; only placed clones replicate. Source PNG IHDR and manifest confirm every military map is 256×256 (all 40 maps), not 1024+. With uncompressed RGBA8 and a full mip chain, 256² × 4 bytes × 4 maps × 4/3 ≈ 1.33 MiB per unique kit asset: M03 ≈2.67 MiB, M02 ≈1.33 MiB, M01 zero. All ten would be 13.33 MiB, but are not all placed in M03. Do not multiply texture storage by the 13 clones: content is reused; actual GPU formats, streaming/mips and decoder/cache copies are unknown. This modest estimate weakens “huge military textures alone” as the explanation. Mesh/appearance overhead and a cold preload spike remain possible.
   - Mitigation: M03 explicitly opts out of uploaded decoration in adoptGroundTarget, even for cached templates. No military load request or clone/PBR instance in M03; every target uses its existing procedural geometry and aim/collision root. This intentional temporary visual degradation applies to all devices, before replication/preload, preventing any restoration by local LOD code. #220 accounting/fallback remains intact for other missions.
   - MissionPreload calls PreloadAsync once on ALL mission MeshParts/other content, with a six-second watchdog that does not cancel the engine load. The military removal eliminates all 13 military entries from that batch. Aircraft meshes remain.
3. **Another construction/session exception (unconfirmed).** #220's cap arithmetic remains sound: 145 base descendants below 148; 13 bounded decoration models account separately. No additional M03 throwing part/mesh/sector cap found. The per-kit 24-instance cap rejects before hiding proxies. CombatService checks ground target counts and stationary aim roots inside pcall and returns a visible retry error. Log original error with mission, last world phase and elapsed time BEFORE destroying the folder/starting cleanup so the useful failure survives recovery trouble.
4. **Planning CPU or gorge geometry (low confidence here).** Standalone baseline profile: layout ~0.006 s; complete plan ~0.73 s, max checkpoint gap ~0.024 s on this host. These are CLI timings, not device/Studio acceptance. Loops are finite; terrain Fill calls are chunk-bounded at 65,536 voxels and execution yields on an 8 ms budget. Gorge height and clearance logic are unchanged. #205's broader planner/cleanup work remains separate.

## Memory comparison and limits

- StreamingEnabled is explicitly false in both place projects, so this large workspace does not use instance streaming. Enabling it globally needs flight/target replication work; this urgent patch keeps that separate.
- M03's axis-aligned planned terrain intersects 140,016 distinct 128-stud 3D bins before removal and 81,452 after: 58,564 fewer (41.8%). The floor is wholly in negative-Y bins while the rest starts at Y=0, so those bins are disjoint. These are geometric bins, not measured engine allocation units.
- Removing 59,969,536 written cells represents about 114.4 MiB of logical payload IF a cell used two bytes (material + occupancy); this is an illustrative uncompressed representation, not a Roblox resident-memory estimate. Compression, sparse allocation, meshing, replication and transient buffers prevent a defensible actual MiB claim. Expect substantial terrain pressure reduction, but not a guaranteed 42% total-process saving.
- Pure counts: M01 207,739,968 writes / 27,494 jobs / 955 descendants; M02 175,062,192 / 14,706 / 1,164; M03 before 206,784,672 / 30,590 / 146 (145 base descendants within scene), after 146,815,136 / 29,566 / 146. Write totals alone do not predict resident terrain memory; the thin negative-Y floor creates a wide additional allocation band.
- MobileGraphics disables bloom/sun rays/depth of field and trims clouds; it does not lower terrain resolution or strip PBR. M03 has clear weather and no opening explosions/particle burst in its builder; lights/post-effects are less supported causes of an immediate launch exit. Gorge resolution remains unchanged.
- [Roblox optimization guidance](https://create.roblox.com/docs/performance-optimization/improve) recommends content reuse and streaming for large worlds with memory issues. [Memory categories](https://create.roblox.com/docs/studio/optimization/memory-usage) distinguish terrain, textures and cache. Estimates above derive from repository bytes/plans, not measured device memory.

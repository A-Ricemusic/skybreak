# Military kit load investigation — 2026-11-01

Scope: main `3ed084dd`; supplied `/tmp/sq-main/build/jest-studio.log`, read-only. No Studio, Player, uploads, credentials or deployment in this investigation.

## Findings

1. **The 8×8×8 warnings are test doubles.** `src/tests/WorldInstanceBudget.spec.ts` on main configures `UploadedAssets` with a loader creating two overlapping `new Instance("MeshPart")` objects, explicitly sets both `Size = new Vector3(8,8,8)`, and supplies a probe returning true for every appearance map. It labels these fixtures with the ten real military IDs. Every test clears the cache/failure set through `Configure`. This explains the repeated warnings under real IDs without any request to Roblox. Main's log starts this cluster at line 3931 (22:34:28.954Z), and reports the failing suite at line 4310. These are not evidence of a Studio engine regression or an uploaded placeholder.
2. **Production path:** `WorldAssets.Preload` → `UploadedAssets.Preload` → `Template` → `InsertService.LoadAsset` → `normalise`. No `CreateMeshPartAsync`, `AssetService`, content preload or readiness wait. Normalisation clones/sanitises parts, validates their appearance, applies orientation, immediately calls `GetBoundingBox`, checks `FitScale`, scales uniformly and recentres the pivot. It measures BasePart extents, not decoded mesh vertices. The server/game and Studio use this same normalisation, but this spec replaces the actual load operation. Thus a real malformed upload would take the procedural fallback in live too; the supplied warnings do **not** establish that this is occurring. Live appearance remains unobserved. M03 intentionally never requests/places the military kit after #236.
3. **Guard is correct:** `AssetSelection.FitScale` rejects nonfinite/zero dimensions, scale outside 0.001–1000, and deviations greater than 5% of expected longest extent after uniform fitting. A cube cannot represent the tank's 17.52×12×33.5 proportions. Loosening the check or replacing measured dimensions with expected dimensions would accept wrong geometry. Keep it and the failure cache/fallback unchanged.
4. **Size versus mesh readiness:** [Roblox MeshPart documentation](https://create.roblox.com/docs/reference/engine/classes/MeshPart) describes mesh geometry size separately from part size, and [TriangleMeshPart](https://create.roblox.com/docs/reference/engine/classes/TriangleMeshPart) describes the original geometry dimensions. Neither establishes 8×8×8 as a universal unresolved-mesh default. Here 8 is explicitly authored by the test. No evidence justifies assuming `InitialSize` will repair it, changing authored geometry, or adding runtime content waits. Content preload may resolve visual content without changing `Size`; successful fetch alone does not establish correct proportions or appearance.
5. **698.054 s is assembly/planning cost, not 136 network retries.** Fixture loads do not yield and failures are cached until reset. `Preload` starts different IDs in parallel and bounds the caller's wait (world default 30 s); pending engine requests may continue afterward. World builders independently construct dense shell plans and yield from time-sliced checkpoints and every 32 dressing parts / 8 props. Even when TerrainWriter is mocked, terrain planning still runs. Log case times range from M18 1.859 s to M15 102.553 s; the second M03 test hits the runner's default 20 s deadline (20.050 s). The log truncates detailed later failure traces, so it does not establish another M03 assertion failure.

## Changes and remaining acceptance

Assembly fixtures now use each asset's authored proportions and synthetic IDs; all ten are preloaded once per suite and asserted ready. A regression checks that cubes still fail once, preserve the proxy, and are not retried. Assembly tests suppress frame waits through a shared `WorldBuildScheduler.Pause` seam (production still calls `task.wait()` at every original boundary), cache the complete M03 plan used by the expected-count assertion instead of regenerating it inside that timed case. Complete production terrain plans are still generated by world builders. Compact-world sea parts and all dressing/targets remain real. Terrain writes remain mocked, with terrain topology checked by existing offline contracts; this suite still exercises plan generation and every dressing/target instance. Per-call fixture waits are 0.25 s; fixture loads are synchronous. Studio runtime reduction is **not measured** in this branch.

`MilitaryKitDiagnostic.spec.ts` is disabled unless the isolated Jest place has `Workspace.MilitaryKitDiagnostic=true`. When enabled it directly loads only the real MilitaryTank ID, logs hierarchy/classes, CFrame/Size, MeshId, MeshContent, MeshSize, InitialSize and HasMesh (including unavailable/security errors), then logs content fetch status and the same snapshot after `ContentProvider.PreloadAsync`. An 8 s outer deadline cancels the worker and destroys the container; it never parents it into Workspace. No upload or key is needed. Interpret outcomes:

- Correct raw bounds immediately: supports fixture-only failure; no readiness correction indicated.
- Wrong raw bounds that become correct after preload: supports an actual readiness race; use this evidence to design a bounded production wait before cloning/measurement.
- Correct bounds with initially missing geometry/fetch pending: content readiness issue, distinct from bounding-box plausibility.
- Persistent cube bounds, valid nonempty mesh IDs/content and completed fetch: supports wrong authored/container geometry; inspect the uploaded asset rather than bypassing the guard.
- Empty mesh IDs/content, unexpected BasePart classes or placeholder hierarchy persisting after preload: supports a placeholder/wrong asset result, with procedural fallback appropriate.
- Timeout, fetch failure or unreadable properties: inconclusive; retain fallback and collect server/Studio evidence. No live conclusion follows from a Studio-only diagnostic.

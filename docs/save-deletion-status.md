# Save deletion durability

The audited defect was `CampaignService.deleteSlot` ignoring `flush()`'s boolean and returning local acceptance as though it confirmed a cloud delete. `GameUI` inferred success from `persistence`, which can remain `cloud` while a write exceeds the flush deadline.

`CampaignResponse.ok` still means the command was accepted. The additive `deletions` receipts identify the slot and deletion generation separately from profile persistence:

- `confirmed`: a successful cloud update returned the empty slot at the exact tombstone generation sent by that write. UI: “deletion confirmed in cloud.”
- `pending`: its write is scheduled or running, including after the five-second flush deadline. UI: “deleted here; cloud confirmation pending. It may return next session.”
- `failed`: no confirmation and no write scheduled/running (including exhausted attempts or a write that did not persist the tombstone). UI: “deleted here; cloud deletion is unconfirmed after saving. It may return next session.” The local deletion remains accepted; the existing dirty-save recovery contract is preserved.
- `session-only`: no store exists. UI: “deleted for this session only. Cloud saves are disabled.” A successful session flush cannot mean cloud confirmation.

For pending deletion the UI checks the read-only `DeletionStatus` action every three seconds, at most ten times, and displays late confirmation or failure. Every screen transition invalidates a separate observation epoch, including leaving and returning to the same screen. New requests or unmount also stop observation. The epoch is captured before the initial delete RPC and checked before and after each yielding status RPC, so navigation during either RPC cannot deliver a stale toast. Foreground request ownership is independent. A transport failure, cancelled observation, or expiry leaves the last pending warning; it never manufactures confirmation. These checks neither retry deletion nor trigger writes. Status reads have a separate per-player 500ms budget and require an already loaded, non-closing session; they never acquire the foreground busy lock or mutate the 120ms command budget. Foreground commands retain their existing rate limit and lock. Future responses also carry current receipts. No new remotes or persistence schema fields are introduced. Receipts live only for the current coordinator session.

Existing save retries continue to merge snapshots using generation tombstones. A late successful tombstone write can confirm the original deletion while newly recreated local progress remains intact and is drained next. A recovery write containing recreated progress does not pretend the empty tombstone itself was confirmed. No status check calls `deleteSlot`, and no automatic destructive retry is added. Confirmation records that the tombstone was acknowledged, not that another session can never write newer progress.

Validation uses synthetic in-memory stores only, injected clock/wait functions, and the standalone Luau CLI. Cases cover successful write, exhausted write, scheduled/inflight deadline expiry, late success/failure, session-only mode, successful recovery, and recreated-slot safety. `bun run build` and the offline domain suite suffice for this change; no Studio, published place, DataStore, or real user save is accessed. Focused offline tests exercise observation cancellation before dispatch and during a simulated yielding RPC, stale notification suppression, independent rate budgets in both orders, status spam, overlapping deletions and conflicting store receipts. Actual React/Roblox scheduling, RemoteFunction transport, authenticated cloud persistence/rejoin and rendered toasts remain unverified; Studio was not used because flight54 owns it.
